# Engine-driven camera nudges, clickable props, and ambient life across the four frankfabric demos (v1)

WS3 makes all four 3D demos (chef, coach, pet, wardrobe) react to the app's own logic instead of standing still. Each engine (chef/coach) gains a purely additive `focus` read-out that names the branch `respondToMessage` already picked; each scene layers a small `damp3` camera nudge over its pinned framing keyed off that read-out (or the pet's existing transient action / wardrobe's selection-change signal), adds exactly one clickable procedural prop whose handler dispatches a real query/action through the existing input path, and adds cheap procedural ambient particles with the heavier variant gated to `quality === 'high'`. No new dependency, asset, or build output is committed, and nothing in tireshop is touched.

Watch for: the wardrobe `CameraRig` is the one rig that mutates the camera *relatively* (`addScaledVector` along the view direction) on top of OrbitControls rather than writing an absolute `pinned + offset` like the other three — worth understanding why it doesn't drift (confirmed). Everything else routes cleanly through the existing layer and the engines' reply/suggestion text is byte-identical.

**Verdict**: APPROVED

## High-level view

The routing contract holds everywhere. Scenes import the engines only as types (or, for wardrobe, the pre-existing `OPTIONS` content module); no scene holds recipe/workout answer text or stat math. Chef and coach clicks call the chatbot's existing `send("Suggest a recipe"/"Suggest a workout")`, the pet click calls the existing `doAction("play")` → `decayForElapsed`+`applyAction`, and the wardrobe hit-boxes call `cycleCategory` → the existing selection setter over `OPTIONS` via the new pure `nextIndex` helper. There is no parallel state machine and no answer invented in a component.

Engine behavior is preserved. The `focus` field is optional and additive; every existing return branch got a `focus:` tag and the two LLM-spread branches were wrapped as `{ ...replyFromLlm(...), focus: "suggest" }`. Reply strings, suggestion chips, and input parsing are unchanged.

Pinned-constant discipline holds for chef/coach/pet: each rig keeps `PINNED_CAM`/`PINNED_LOOK` as read-only constants and writes `camera.position = pinned + easedOffset`, with the offset decaying to zero via a pulse, so the locked shot always reconverges. The wardrobe rig is different by necessity (OrbitControls owns the camera each frame) and applies a transient relative dolly that relaxes to zero without touching any OrbitControls prop.

Perf is preserved. Heavier ambient motion and particle counts are `high`-only; the Fast path keeps a small always-on variant. Measured Fast medians are identical before/after (chef 66.7 ms, coach 83.3, pet 183.3, wardrobe 83.3) and High medians are within rasterizer noise.

Hygiene is clean: no `package.json`/lockfile change (`maath` is already a direct dependency of drei; `useCursor` ships with drei), no external asset (sprites are in-memory canvas textures), and only `docs/motion/` PNGs/JSON plus the 11 expected source files are in the diff. `npm run lint` is clean but for the pre-existing allowed font warning, and `npm run build` static-exports all five routes.

### Routing through the existing layer

Every new interaction reaches the app's existing logic, and no scene classifies intent or holds answer content. `ChefScene`/`CoachScene`/`PetScene` import their engines only via `import type` (`ChefFocus`, `CoachFocus`, `PetAction`); `grep` for value imports of `respondToMessage`/`applyAction`/`OPTIONS` in the four scene files returns nothing for the engines. The clickable props are pure dispatchers: `SampleDishProp`/`KettlebellProp` take an `onClick` that the chatbot wires to its own `send("Suggest a recipe")` / `send("Suggest a workout")`, so the reply is produced by `respondToMessage` exactly as if typed. The pet's clickable dog calls `onPetClick={() => doAction("play")}`, and `doAction` is the same `decayForElapsed`→`applyAction`→persist path the on-screen buttons use (`VirtualPet.tsx:179`, `:297`).

Wardrobe is the subtle one because the scene legitimately needs the content list to know how many options a category has. It does not carry that list itself: `WardrobeScene` already re-exported `OPTIONS` on `main` as the content source of truth, and the new `GarmentHitbox` meshes only map a body region to a category name (`"torso"→"outfit"`, `"legs"→"bottom"`) and call `cycleCategory`. `cycleCategory` lives in `WardrobeBuilder` and computes the next index with the new pure `nextIndex(category, current)` helper in `wardrobeOptions.ts`, then routes through the same `setOption` the menu cards use — so a 3D click and a menu click are indistinguishable to the rest of the app. The wrap math is a single `(current + 1) % len` in the content module, not in the scene.

### `focus` read-out is additive and behavior-preserving

`ChefResponse`/`CoachResponse` gain an optional `focus?` field; the new `ChefFocus`/`CoachFocus` unions name the branch that `respondToMessage` already chose. Each existing `return` got a `focus:` tag matching its branch, and the two branches that returned `replyFromLlm(...)` were rewrapped as `{ ...replyFromLlm(llmResult, opener), focus: "suggest" }` — spreading the identical object and adding one field. Filtering the engine diff's `+` lines for anything other than `focus`/comments/structural braces surfaces only the two spread wrappers, confirming reply text, suggestion chips, and the parser are untouched. The chatbots read `response.focus ?? null` straight off the response and bump a `focusNonce` so an identical focus re-fires the nudge; no intent is derived in the component.

### Pinned-constant discipline and the wardrobe exception

Chef, coach, and pet share one safe pattern: `PINNED_CAM`/`PINNED_LOOK` are module constants, and each frame the rig eases an additive offset toward a per-focus/per-action target scaled by a `pulse` that decays to zero over ~1.2 s, then writes `camera.position.set(PINNED + offset)` and `camera.lookAt(PINNED_LOOK + lookOffset)`. Because the pulse relaxes to zero even while a focus lingers, the camera always reconverges to the locked shot, and the pinned constants are never mutated (offsets are written into fresh `useRef` vectors). Pose deltas are centimetre-scale.

```
chef/coach/pet:   camera.position = PINNED_CAM + damp3(offset -> target*pulse)   // absolute, self-correcting
wardrobe:         camera.position += forward * -offset.z  (offset.z -> 0)         // relative, on top of OrbitControls
```

The wardrobe rig cannot use the absolute pattern because OrbitControls owns the camera transform every frame (turntable `autoRotate`, user orbit). Instead it dollies the camera along its current view direction by an eased amount that peaks at −0.16 m and decays to zero, and adds a small vertical bias. This is the one place to look closely: it is a *relative* mutation, so if the offset ever failed to return to zero it would accumulate. Traced through, it does return to zero (the `damp3` target is `dolly * scale` with `scale = pulse → 0`), and OrbitControls recomputes position from its own spherical state (target `[0,1.1,0]`, clamped `minDistance` 1.4 / `maxDistance` 5) on its next frame, so the nudge reads as a brief dolly that relaxes rather than a persistent shift. No OrbitControls prop (`target`, `minDistance`, `maxDistance`, `autoRotate`, `enablePan`, polar limits) is changed — the diff's only matches for those names are in comments.

Tone mapping and the skin/hair/brow tint pipeline are not touched: filtering added lines for `toneMapping`/`exposure`/`ACESFilmic`/`skin`/`tint` yields only comment text.

### Quality gating and measured frame time

Each ambient effect scales particle count and drift by a `high` flag (steam wisps 26 vs 10, dust motes 20 vs 7, atelier motes 22 vs 8), keeping a small always-on variant on Fast. Ambient geometry and canvas sprite textures are created in `useMemo` and disposed on unmount, and the per-frame loops write into a preallocated position buffer with no per-frame allocation.

Measured on this machine (Linux x86_64, headless Chrome 151.0.7922.10, ANGLE/SwiftShader software rasterizer, 1280×900), the docs report Fast-path medians identical before/after:

```
          Fast median (ms)      High median (ms)
chef       66.7 -> 66.7          83.3 -> 83.3
coach      83.3 -> 83.3          83.4 -> 83.5
pet       183.3 -> 183.3        283.3 -> 283.3
wardrobe   83.3 -> 83.3         116.7 -> 116.7
```

Absolute numbers reflect a software rasterizer and are not hardware-representative (the docs say so); only the relative before/after comparison is meaningful, and it shows no Fast regression, which is the load-bearing claim. p95 values wander in both directions (chef high p95 100→133.3, pet fast p95 383.3→416.6) but that is expected jitter on SwiftShader at ~12–15 fps and the medians are the stable signal.

### Dependency and asset hygiene

No `package.json` or `package-lock.json` change. `maath` resolves as a direct dependency of `@react-three/drei` (`^0.10.8`) and `useCursor` is a drei export, so `maath/easing` and `useCursor` add no new runtime dependency. Every ambient sprite is a `THREE.CanvasTexture` drawn into an in-memory canvas — no external image asset. The diff contains only the 11 expected source files plus `docs/motion/` evidence; no `node_modules/`, `out/`, `.next/`, `assets-src/`, or model files, and no tireshop path.
