# WebP asset compression and three-chunk code-split for frankfabric (v1)

Workstream 1 attacks frankfabric's worst problem — multi-megabyte cold loads dominated by embedded VRM/GLB textures and a ~913KB three.js chunk statically preloaded by the wardrobe page. Three commits deliver it: a measurement-only Playwright harness plus a committed baseline, a re-runnable chunk-level GLB/VRM rewriter that re-encodes embedded textures to WebP (`public/models` 56M→17M), and a code-split that pulls the wardrobe UI's `OPTIONS` value out of the three-heavy scene module so the page stops preloading three, backed by a real `useProgress` Suspense fallback across all four scenes. Cold-load bytes drop −50.5% on wardrobe and −31.2% on pet; the largest JS chunk referenced by any prerendered HTML drops −77.7% raw. Screenshots are proven identical via a color-histogram TV-distance metric that isolates real regressions from animation-phase drift.

Watch for: three eager FBX animation clips (~2.57MB) still load on wardrobe scene mount though only the rest pose is shown initially — the one place the "load only the initial view" goal is incompletely met (possible). `sharp`, the compressor's engine, is only a transitive dependency, not declared (possible). Chef/coach are ~flat by design because their external FBX/OBJ textures were deliberately left uncompressed (confirmed, documented). No runtime dependency was added; tireshop is untouched.

**Verdict**: APPROVED

## High-level view

The compression is a hand-rolled GLB container rewrite rather than a gltf-transform round-trip, and that choice is correct: gltf-transform's default IO silently drops VRM extensions (MToon, spring bones) on write. The script re-encodes only image bufferViews, refuses any image view shared with an accessor, only adopts WebP when it's actually smaller, and reads from a gitignored pristine `assets-src/` tree so it never recompresses its own output. WebP (not KTX2/Basis) is the right format here because frankfabric tints via `material.color.copy()` on MToon/MeshStandard materials — there is no canvas pixel-readback tint pipeline, so no GPU-compressed-texture constraint applies and GLTFLoader decodes WebP with no runtime decoder.

The code-split is durable, not incidental. The three chunk was preloaded because `WardrobeBuilder` imported the `OPTIONS` runtime value from the three-heavy `WardrobeScene`; moving `OPTIONS` and the shared types into a zero-three `wardrobeOptions.ts` module and re-pointing the builder there breaks that static edge. `WardrobeScene` re-exports the same symbols so nothing else breaks, and the builder now imports only from the light module. All four scenes remain `next/dynamic { ssr:false }` and asset()-routed; the heavy chunk still exists but loads only on scene mount.

The `useProgress` fallback lives inside each Canvas's `<Suspense>`, exactly where `fallback={null}` used to be, so it has the R3F context `useProgress` and `<Html>` need. It renders only DOM chrome — no meshes, lights, camera, or tone-mapping touches — so it can't perturb how any scene renders once loaded.

The evidence is honest about animated scenes: chef/coach diff bit-for-bit, wardrobe/pet differ only in animation phase, and the ~0 color-histogram TV distance across all four confirms tone mapping, exposure, tint constants, and textures are unchanged.

## Chunk-level GLB rewrite preserves VRM extensions

The compressor parses the GLB container by hand — 12-byte header, JSON chunk, BIN chunk — re-encodes only the bufferViews that `images[]` point at, rebuilds the BIN with 4-byte alignment, and patches `bufferViews[].byteOffset/byteLength`, `images[].mimeType`, and `buffers[0].byteLength`. The stated reason is that gltf-transform's default NodeIO does not know `VRMC_vrm`, `VRMC_springBone`, `VRMC_materials_mtoon`, etc., and drops them on write, degrading a VRM into a plain glTF with broken MToon and spring bones. Confirmed by inspecting the rewritten `schnauzer.glb`: its JSON still carries `image/webp` on the sole image (bufferView 4) and every geometry accessor/bufferView intact.

Two safety properties matter and both hold. The script builds a set of every bufferView referenced by an accessor and throws if an image view ever intersects it, so a shared view can't silently corrupt geometry. And it only adopts the WebP output `if (encoded.length < src.length)` — otherwise it keeps the source bytes — so tiny maps that beat WebP are never inflated. Normal maps and face/skin/eyes/mouth maps get a conservative policy (1536px, quality 90–95) while hair/garment/scan maps go to 1024px/q82; sub-64px lookup maps are skipped entirely.

Idempotency is structural, not best-effort: the script reads from a gitignored `assets-src/` pristine tree and writes to `public/models`, seeding `assets-src/` from `public/models` on first run. Because input and output are different trees, re-running never feeds compressed output back through the encoder. `assets-src/` is correctly gitignored and untracked.

## WebP is the correct format for frankfabric's tint pipeline

The critical distinction from the tireshop reference: frankfabric has no `getImageData`/`readPixels` canvas pixel-readback tint pipeline (grep across `components` and `lib` returns nothing). Tinting is `material.color.copy(color)` on the MToon and MeshStandard materials in `lib/vrm/transplant.tsx`. Textures are never read back on the CPU, so there is no requirement to keep them in a canvas-decodable-only format — and no benefit to KTX2/Basis, which would need a runtime transcoder dependency. WebP is GLTFLoader-decodable with zero runtime wiring and adds no dependency.

## Code-split removes the static three edge from the wardrobe page

```
BEFORE                                   AFTER
WardrobeBuilder ──imports OPTIONS──►     WardrobeBuilder ──imports OPTIONS──► wardrobeOptions.ts
  WardrobeScene (three/@react-three/       (zero three imports)
  @pixiv-three-vrm)                      WardrobeScene ──re-exports OPTIONS──► wardrobeOptions.ts
  ⇒ three chunk in static page bundle      (three loads only on dynamic mount)
```

The re-export in `WardrobeScene.tsx` keeps every existing importer of that module working, and the builder was re-pointed to import `OPTIONS` and the types only from `wardrobeOptions.ts`. A grep for other importers of `WardrobeScene` finds only the `next/dynamic(() => import(...))` in the builder (which is exactly the deferred edge we want) — no runtime value import re-leaks the heavy module into a static bundle. The measured result: the largest JS chunk referenced by any prerendered `index.html` drops 913,347→203,384 B raw / 238,951→63,950 B gzip, and `grep -rl <chunk>.js out/**/*.html` finds no prerendered HTML referencing the ~922KB three chunk.

All four scenes set `gl.toneMapping = THREE.ACESFilmicToneMapping` unchanged, and all four remain `ssr:false` dynamic with `asset()`-routed URLs. No hardcoded `/models/...` path was introduced.

## Deferred loading: landing ships zero model bytes, wardrobe loads only the default look

`after-landing.json` has no `.vrm` or `.glb` entries — the heavy three code and every model stay behind the `ssr:false` wrappers. The wardrobe cold load fetches exactly the 6 default VRMs (body, eyes, default hair/top/bottom/shoes ≈ 2.25MB); the other ~30 garments load only when their option is selected via `<Garment url=…>`, and no eager `useGLTF.preload` of the full set was added.

The remaining gap: `WardrobeScene`'s `Avatar` calls `useLoader(FBXLoader, ANIMATION_URLS.idle/walking/waving)` at mount, so all three animation clips (idle 1.58MB, walking 0.37MB, waving 0.62MB ≈ 2.57MB) stream in on the initial wardrobe load even though the default view sits in the auto-rotating rest pose with no clip playing. These are the single largest deferrable item left on that route; loading them when an animation control is first used would apply the same on-demand pattern the garments already follow. Not blocking for this pass — the −50.5% target was met — but it's the clearest place the "initial view only" principle isn't fully realized.

## Screenshot identity is proven, not asserted

The `DIFF.md` metric pairs a per-pixel diff with a motion-invariant color-histogram total-variation distance. Chef and coach come out bit-for-bit (0.000 mean diff), which also proves the capture pipeline introduces no tone/color shift. Wardrobe (1.05 mean, TV 0.0020) and pet (5.85 mean, 11% edge pixels, TV 0.0044) differ only on subject silhouette edges, attributed to the wardrobe turntable auto-rotate and the pet's always-on breathing bob landing on different animation frames — the R3F render loop is not frozen by Playwright's CSS `animations:'disabled'`. The ~0 TV distance across all four is the load-bearing evidence: identical color distributions mean the ACES operator, exposure, MToon/material tint constants, and textures are unchanged, and no pose/transform number is eyeballed.

## Dependency and repo-scope posture

The only added dependency is `playwright-core` (devDependency, `^1.63.0`) for the measurement harness — user-approved, measurement-only, never shipped to the browser (it drives an on-machine Chrome via `executablePath`, no browser download). No runtime dependency was added; no KTX2/Basis/Draco/meshopt runtime wiring was introduced. `sharp` is used by the build-time script via `createRequire` but is only present transitively — flagged above as a declaration gap, not a runtime concern. The diff is entirely within frankfabric; the reference repo at `/projects/sandbox/tireshop` has a clean working tree and was not modified (it lives in a separate git repo, and the frankfabric diff touches only frankfabric paths).
