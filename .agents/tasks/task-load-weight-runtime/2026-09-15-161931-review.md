# On-demand wardrobe animation clips and declared sharp devDependency (v2)

This follow-up commit (`a599122`) closes two of the four non-blocking issues the v1 review left open on Workstream 1. The wardrobe scene no longer eagerly `useLoader`s all three Mixamo FBX clips at mount; each clip now streams in on demand through a per-clip `<ClipLoader>` gated by a `requested` set seeded from the initial `animation` prop, so a cold load fetches only `idle.fbx` and defers `walking.fbx` + `waving.fbx` (~0.99MB) until first selected. The single-mixer / retarget / crossfade wiring is preserved via a `useMemo` mixer, a callback that registers each retargeted clip against it, and a crossfade that re-evaluates both on `animation` change and on clip registration. Separately, `sharp` (the compressor's image engine) is now declared in `devDependencies` rather than relied on transitively. Wardrobe cold load drops a further 993KB (9,241,579 → 8,248,182 B, −55.8% vs the 18.671MB baseline); lint and static build stay green.

Watch for: the wardrobe screenshot's per-pixel diff rose (TV 0.0020 → 0.0073, 1.5% → 5.5% edge pixels) but this is idle-crossfade capture-phase drift, not a render regression — the motion-invariant color-histogram TV stays ~0, below the pet scene's 0.0044 (confirmed). The animation-deferral rework is the only behaviorally-risky change and its mixer/register/crossfade ordering is sound (confirmed). v1 issues #3 (schnauzer geometry-bound) and #4 (thumbnail PNGs) were intentionally left out of scope, which is acceptable.

**Verdict**: APPROVED

## High-level view

The animation deferral reuses the garment on-demand pattern: a `requested: Set<ClipName>` gates which `<ClipLoader>` components mount, and each loader suspends on its own FBX in its own `<Suspense fallback={null}>`, so streaming a newly-selected clip never blanks the already-rendered avatar. The set is seeded from the initial `animation` prop (default `"idle"`), so idle loads on cold start and the other two defer — which is exactly what the byte measurement confirms.

The subtle part is the mixer lifecycle, and it is handled correctly. The mixer is a `useMemo` value (not a ref written during render), so it exists before any child `ClipLoader` effect runs — child effects fire before parent effects on the same commit, which is precisely why building the mixer in a parent effect would have stranded the avatar in a T-pose. Each ClipLoader retargets its FBX and hands the *clip* (not a pre-built action) to `registerClip`, which builds the action from the shared mixer, keeping every clip on one timeline. The crossfade re-evaluates on `animation` change and again when a clip registers, so a clip picked before its FBX arrives fades in the moment it lands. Growing the mixer/actions across an avatar rebuild is handled by not clearing `actions.current` on teardown and letting each child effect re-register against the new mixer.

The `sharp` change is build-time only: it is imported solely by `scripts/compress-assets.mjs` and `scripts/convert-avatar-jpeg.mjs`, never from any file under `app/`, `components/`, or `lib/`, so it cannot leak into a browser bundle. Moving it from a transitive edge to a declared `devDependency` removes the silent-break risk v1 flagged.

The compression script, code-split, and `useProgress` fallback from v1 are untouched by this commit and were already approved; the follow-up did not disturb them, and the chef scene that shares `retarget.ts` is unchanged apart from its v1 SceneLoader swap.

## Animation deferral: mixer, registration, and crossfade ordering

The rework replaces three mount-time `useLoader(FBXLoader, …)` calls and a single `playback` ref with a `requested` gate, a `useMemo` mixer, a per-clip `<ClipLoader>`, and a `useCallback` crossfade. The pieces fit as follows:

```
animation prop ──┐
                 ├─► requested: Set<ClipName>  (seeded from initial animation)
 selection ──────┘        │
                          ▼
        {requested}.map ─► <Suspense fallback={null}><ClipLoader/></Suspense>  (one per requested clip)
                                        │  suspends on its own FBX, retargets
                                        ▼
                             registerClip(name, clip)
                                        │  actions.current[name] = mixer.clipAction(clip)
                                        ▼
                                 applyCrossfade()  ◄──── useEffect on [applyCrossfade] (animation change)
                                        │
                                        ▼
                              useFrame: mixer.update(delta); vrm.update(delta)
```

The gate is grown with the "adjust state during render" pattern — `if (animation !== "rest" && !requested.has(animation)) setRequested(...)` runs in the render body, not in an effect, so the new `ClipLoader` mounts in the same commit that reflects the selection and there is no setState-in-effect cascade. `requested` only grows, so once a clip is fetched it is never unmounted or refetched during the session.

The mixer being a `useMemo` value rather than a render-time ref write is the load-bearing correctness decision. Because a child effect runs before its parent's effect on the same commit, a `ClipLoader` mounted in the same commit as the mixer would try to call `mixer.clipAction` before a parent effect could have created it. Sourcing the mixer from `useMemo(() => new THREE.AnimationMixer(vrm.scene), [vrm])` guarantees it exists during the child effect. The comment block documents this as the fix for a T-pose bug, and the reasoning holds.

The two paths that can strand the avatar were both checked:

- *Clip selected before its FBX arrives.* Selecting `walking` adds it to `requested`; the ClipLoader mounts and suspends. Meanwhile the `applyCrossfade` effect fires with `animation === "walking"` but `actions.current.walking` still null — the guard `if (animation !== "rest" && !next) return;` bails without touching `currentAction`, so idle keeps playing. When the FBX resolves, `registerClip` fills `actions.current.walking` and calls `applyCrossfade` again; now `next` exists, `prev` is idle, they differ, so walking resets/fades in and idle fades out. Correct — no stuck pose.

- *Avatar (`vrm`) rebuild.* The teardown effect deliberately does not clear `actions.current`. On rebuild the mixer `useMemo` recomputes, each ClipLoader's effect re-runs (it depends on `vrm`), its cleanup fires `register(name, null)` and the new run fires `register(name, clip)` against the new mixer. The comment's reasoning — that clearing `actions.current` in the parent teardown would race ahead of the child re-registration and wipe a just-registered clip — is consistent with child-before-parent effect ordering. The stale action faded out in that window belongs to the stopped old mixer, so fading it is harmless.

`applyCrossfade` depends only on `[animation]` and reads refs (`actions.current`, `currentAction.current`) for everything mutable, so it is stable across clip loads except when the selection changes — which is the intended trigger. `registerClip` depends on `[applyCrossfade, mixer]`. The `FADE = 0.35`, `reset()/setEffectiveWeight(1)/fadeIn/play` sequence is carried over verbatim from the pre-follow-up crossfade, so the fade feel is unchanged.

Asset URLs still resolve through `ANIMATION_URLS`, which is built from `asset("/animations/*.fbx")` — the `lib/asset.ts` base-path helper — so production URLs stay under `/frankfabric/`. The default view is unchanged: the builder still defaults `animation` to `"idle"`, the same clip that played on the default view before, and the auto-rotate-at-rest behaviour is untouched.

## sharp is build-time only

`sharp` is imported by `scripts/compress-assets.mjs` (`require('sharp')` via `createRequire`) and `scripts/convert-avatar-jpeg.mjs` (`import sharp from "sharp"`) — both one-shot Node scripts under `scripts/`, never referenced from `app/`, `components/`, or `lib/`. Declaring it in `devDependencies` (`"sharp": "0.34.5"`, exact-pinned) with the lockfile updated removes the transitive-edge fragility v1 called out without adding anything to the browser bundle.
